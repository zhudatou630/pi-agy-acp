# Pi v1.6.0 extension API: wrapping `agy acp`

**Recommendation:** register a physical chat provider with a distinct API ID. Let one Pi provider request consume one complete ACP prompt response. Stream ACP text and thoughts as Pi assistant blocks; show tool progress and plans via a widget, and persist a redacted summary as a `custom` entry if needed. **Do not emit Pi `ToolCall` blocks merely to display ACP activity:** they ask Pi to execute a tool after the assistant response. A proxy tool can produce native tool rows, but it changes turn boundaries and adds a continuation protocol.

**Evidence and scope.** Read-only inspection of the installed v1.6.0 packages and the installed pi-web v1.8.3 bundle; no `agy`, Pi, or browser session was run. The ACP update types are the premise of this report, not a certification of which features this `agy` build advertises. Citations below are `file:line` in the installed artifacts, not upstream `main`. `CA` = `pi-coding-agent`, `AI` = `pi-ai`, `AG` = `pi-agent-core`, all under `<pi-web 全局安装目录>/node_modules/@earendil-works/`; `WEB` = `<pi-web 全局安装目录>/`（即 npm 全局 `node_modules/@calmabacus/pi-web/`）. Versions: `CA/package.json:2-3`, `AI/package.json:2-3`, `AG/package.json:2-3`, `WEB/package.json:2-3`.

## 1. Provider registration, model metadata, and stream contract

### Registration and refresh

```ts
pi.registerProvider(provider: Provider): void;
pi.registerProvider(name: string, config: ProviderConfig): void;
pi.unregisterProvider(name: string): void;
```

`CA/dist/core/extensions/types.d.ts:1403-1418`. Register in the default factory so startup selection and `--list-models` can see it; Pi awaits async factories. `Api` permits custom strings (`KnownApi | (string & {})`); e.g. provider ID `antigravity`, API ID `antigravity-acp`. The legacy custom callback **requires `config.api` itself** and is used only for `model.api === config.api` (even on the composed provider’s full `stream` path); a per-model API override does not register another custom dispatcher. `CA/docs/custom-provider.md:19-30,117-124`; `AI/dist/types.d.ts:20-27`; `CA/dist/core/provider-composer.js:342-391`.

**Complete legacy `ProviderConfig` shape** (all properties optional at the type level; runtime requirements below), from `CA/dist/core/extensions/types.d.ts:1458-1561`:

| Field | Type / behavior |
|---|---|
| `name`, `baseUrl`, `apiKey` | `string`; provider display name, endpoint default, configured key. A new legacy chat model needs a nonempty `baseUrl` at model or provider level even for stdio; it is metadata only if your adapter never uses it. `apiKey` supports literal, `$NAME`/`${NAME}`, or `!command`, with `$$`/`$!` escaping. |
| `api`, `streamSimple` | `Api`; custom callback below. API and base URL resolve from model definition first, then provider, then applicable existing model defaults. A new provider without defaults needs explicit values. |
| `headers`, `authHeader` | `Record<string,string>` provider headers, interpolated like keys; `boolean` to inject `Authorization: Bearer <resolved key>`. Leave `authHeader` off for stdio. |
| `models`, `refreshModels` | `ProviderModelConfig[]`; `(ctx: RefreshModelsContext) => Promise<ProviderModelConfig[]>`. A supplied list replaces the whole catalog across operations; omitting it preserves the existing catalog. |
| `oauth` | `{ name, isSubscription?, usesCallbackServer?, login(callbacks), refreshToken(credentials, signal), getApiKey(credentials), modifyModels?(chatModels, credentials) }`. Login and refresh return `Promise<OAuthCredentials>`; `getApiKey` returns a string; `modifyModels` is synchronous; `usesCallbackServer` is deprecated. |
| `images`, `classifiers` | Optional API-keyed implementation maps: `Partial<Record<ImageApi,ProviderImages>>` and `Partial<Record<ClassifierApi,ProviderClassifier>>`. Not needed for a chat model that *accepts* images. |

Image generation: `type: "image"`, `output: ("text" | "image")[]`; classifier: `type: "classifier"`, `contextWindow`. Non-chat implementations use their operation-specific API IDs. The actual chat `Model<Api>` additionally has required `provider`, `api`, and `baseUrl`, and optional `samplingParamsByThinkingLevel` (not a field of the legacy chat definition). `cost` is USD per million tokens: `{input, output, cacheRead, cacheWrite, tiers?}`; optional tiers also specify `inputTokensAbove`. `AI/dist/types.d.ts:647-706`; `AI/dist/providers/model-schema.d.ts:23-46`; `CA/docs/models-configuration.md:26-58`; `CA/dist/core/provider-composer.js:118-142`.

Clamping picks the first supported level at or above the request, then searches down. Pi passes the *Pi* level as `options.reasoning`, normally `undefined` for `off`; translate it yourself if ACP has a matching control. Do not advertise configurable effort just because ACP emits thought text. `AI/dist/providers/model-schema.d.ts:1-19,82-87`; `AI/dist/models.js:701-729`; `AG/dist/types.d.ts:295-300`; `AG/dist/agent.js:305-312`; `AG/dist/agent-loop.js:128-143`; `CA/docs/models.md:114-140`.

### What `streamSimple` actually receives

```ts
(model: Model<Api>, context: TranscriptContext,
 options?: SimpleStreamOptions) => AssistantMessageEventStream
```

The public invocation accepts `Context { messages: Message[]; systemPrompt?: string; tools?: Tool[] }`; the provider receives normalized `TranscriptContext { messages }` with system messages carrying prompt sections and tool changes. Use `getCurrentSystemPrompt(context.messages)`, `getCurrentTools(context.messages)`, or `collapseSystemMessages(context)`; don't read `context.systemPrompt` or `context.tools` in the adapter. `Message` is `SystemMessage | UserMessage | AssistantMessage | ToolResultMessage`; `AgentMessage` also includes coding-agent roles such as custom messages and summaries, converted before dispatch. Use `ctx.modelRegistry.streamSimple(...)` or `.complete(...)` for extension-aware calls; the standalone `pi-ai/compat` function does not see these provider registrations. `CA/dist/core/extensions/types.d.ts:1467-1477`; `AI/dist/types.d.ts:360-450,554-575`; `AI/dist/utils/transcript.d.ts:13-41`; `CA/dist/core/messages.js:84-122`; `CA/docs/extensions.md:1222-1228`.

### Emitting events

Return `createAssistantMessageEventStream()` **synchronously** and run the producer separately. Initialize the message before emitting `start`; this excerpt shows the event mechanics after request setup, not an ACP implementation:

```ts
const stream = createAssistantMessageEventStream(); // from @earendil-works/pi-ai
const output: AssistantMessage = {
  role: "assistant", content: [], api: model.api, provider: model.provider,
  model: model.id, timestamp: Date.now(), stopReason: "pending",
  usage: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0, totalTokens: 0,
           cost: { input: 0, output: 0, cacheRead: 0, cacheWrite: 0, total: 0 } },
};
// In producer, after setup:
stream.push({ type: "start", partial: output });
const block = { type: "text" as const, text: "" };
const contentIndex = output.content.push(block) - 1;
stream.push({ type: "text_start", contentIndex, partial: output });
block.text += delta;
stream.push({ type: "text_delta", contentIndex, delta, partial: output });
stream.push({ type: "text_end", contentIndex, content: block.text, partial: output });
output.stopReason = "stop"; // finalize usage first, when reported
stream.push({ type: "done", reason: "stop", message: output });
stream.end();
```

- `start` precedes content updates on success. `text_*` and `thinking_*`: `*_start` opens an empty block (redacted thinking is an exception), `*_delta` carries `delta: string`, `*_end` carries authoritative `content: string`. `toolcall_start/delta/end` use the same `contentIndex` and `partial`; delta is a JSON argument fragment, end has `toolCall` with parsed object arguments (invalid input can carry `argumentsError`, never execute it). Change the block before emitting. `partial` is shared mutable response-so-far, not an event-time snapshot; don't retain it as one. No `plan` or tool-progress block exists in this union. `AI/dist/types.d.ts:259-291,577-646`.
- Exactly one terminal event: `done {reason,message}` for `stop | length | toolUse | deferred`, or `error {reason,error}` for `error | aborted`, with matching `AssistantMessage.stopReason`. `pending` is partial-only. Setup failure may emit `error` without `start`; direct pi-ai paths can also throw on setup/auth, while `ModelRuntime` wraps dispatch in a lazy stream. Always make the final result obtainable; a bare `.end()` with neither terminal event nor result leaves `.result()` unresolved. Use `errorMessage` for failure/abort. `deferred` is a provider fetchable handle, not a way to park a tool until Pi calls again. `AI/dist/types.d.ts:321-351,382-413,592-646`; `AI/dist/utils/event-stream.js:33-109`; `CA/docs/custom-provider.md:180-208`.
- Required final message fields are all those initialized above. Optional fields include `responseId`, `responseModel`, `thinkingLevel`, `providerThinkingLevel`, `diagnostics`, `rawStopReason`, `durationMs`, `endTurn`, `deferred`, and `errorMessage` (the latter two are needed for their corresponding outcomes). `endTurn` is diagnostic only; agent core stamps the requested `thinkingLevel`. `Usage.reasoning` is already included in `output`; `cacheWrite1h` is a subset of `cacheWrite`. Use real counters/costs when available (`calculateCost(model, usage)` for catalog pricing); if ACP supplies none, keep required zeros and describe accounting as unavailable instead of claiming the request was free or estimating billable tokens. `AI/dist/types.d.ts:292-321,382-413`; `AI/dist/models.js:680-699`; `AG/dist/agent-loop.js:272-324`.
- Examples: the checked custom Anthropic extension shows signature/initialization, block-index bookkeeping, streaming arguments, and terminal events (`CA/examples/extensions/custom-provider-anthropic/index.ts:338-374,455-570`), and registration (`:577-612`). It is **not** a complete template for instrumentation; follow the current contract above. GitLab Duo delegates and forwards events while passing through options (`CA/examples/extensions/custom-provider-gitlab-duo/index.ts:301-405`).

## 2. Showing backend tools without asking Pi to run them

### What Pi actually executes

The agent awaits the final assistant message, then decides from the **content**, not solely `stopReason`:

```js
const toolCalls = message.content.filter((c) => c.type === "toolCall");
// ... for a nonempty batch, execute (or synthesize failure for length) ...
for (const result of toolResults) currentContext.messages.push(result);
```

`AG/dist/agent-loop.js:145-193,333-378`. `error`/`aborted` hard-exit before tools. `length` with tool calls synthesizes errors rather than executing potentially truncated input. `stop` with `ToolCall` still executes; `toolUse` alone with no calls is not a continuation. Lookup uses the current **executable** tool list by name; missing tool, invalid args, blocked call, and abort can all produce error results. Natural follow-up carries the final assistant call and matching `role: "toolResult"` messages, plus any queued steering, in the next projected context. Only a wholly terminating tool batch (`every` result has `terminate: true`) suppresses the normal tool-driven follow-up, not other explicit/queued work. `AG/dist/agent-loop.js:96-128,145-213,377-458,478-548,639-670`; `CA/docs/how-pi-works.md:7-23`; `CA/docs/compaction.md:25-49`.

- **Parallel semantics:** default `Agent.toolExecution = "parallel"`; agent-level `"sequential"` or **any** matching tool's `executionMode: "sequential"` serializes the entire batch. Parallel mode emits `tool_execution_start` and performs preflight in source order; starts allowed `execute`s concurrently after preflight; updates/end can interleave; immediate rejected results can end during preflight. Final `toolResult` messages emit in original order. `tool_call` runs after validation and can block/mutate without revalidation; `tool_result` can patch, but isn't called for skipped execution. Do not assume sibling results are visible in preflight. `AG/dist/agent.js:143-148`; `AG/dist/agent-loop.js:373-458,478-537,568-633`; `CA/docs/extensions.md:788-813,973-1013,1040-1074`.
- **Tool UI contract:** `execute(toolCallId, params, signal, onUpdate, ctx)` returns `{content: (TextContent|ImageContent)[], details, ...}`. Use the same shape for partials (`details: undefined` is valid); `onUpdate` emits `tool_execution_update` for that ID, with the latest result displayed by the TUI, not appended as a transcript message. `details` is JSON-safe, persisted with final results and available for rendering/state; only normal result `content` is model-facing, plus normal tool identity/error semantics. Optional `usage`, `structuredContent`, `isError`, `terminate` have separate semantics; throwing yields an error result, returning `isError: true` preserves details. `renderCall(args, theme, context)` and `renderResult(result, {expanded,isPartial}, theme, context)` return a `Component`; context includes ID, cwd, args, `argsComplete`, `executionStarted`, shared row state, last component and final duration/error. `renderShell: "self"` opts out of Pi's box. You can choose a renderer for an unknown tool with `registerToolRenderer`, but this neither makes the tool executable nor hides it from the scheduler. `CA/dist/core/extensions/types.d.ts:473-549`; `AG/dist/types.d.ts:370-407`; `AG/dist/agent-loop.js:538-547,568-597,639-670`; `CA/dist/modes/interactive/interactive-mode.js:3025-3104`; `CA/docs/extensions.md:2123-2132,2274-2309,2523-2650`.
- **Tool registration:** `registerTool` is live (see `CA/examples/extensions/dynamic-tools.ts:23-73`), but runtime allow/exclude filters still apply. `getAllTools()` reports registered metadata, `getActiveTools()` returns names, `setActiveTools(names)` replaces the active set. `defaultActive: false` starts inactive. There is no `unregisterTool`: re-register with `exposure: "hidden"` to withdraw it; inactive `codemode`/`deferred` tools can still be callable by other tools. `model-only` is declared when active but unavailable to `ctx.executeTool`. `prepareLoadout().hiddenDeclarations` can suppress declarations while retaining active execution. Changing active tools changes transcript system tool patches. `CA/docs/extensions.md:1582-1595,1908-1938,2651-2661,2758-2799`; `CA/dist/core/agent-session.js:2980-3057`; `AG/dist/agent-loop.js:217-252`.

### Compare the three display approaches

| Approach | Supported behavior and tradeoffs |
|---|---|
| **(a) `ToolCall` + one registered proxy tool** | Supported **as ordinary Pi tool execution**, not as a provider-executed display marker. It can show a native row, run custom renderers and publish partial results. The provider must first **finish its Pi assistant response** (`toolUse` is the honest reason) while the original ACP operation remains alive. Have the proxy observe an already-started ACP call by validated ID; it must not execute the action again. `execute` can yield partials with `onUpdate`, then a tool result; the next Pi stream drains/resumes the *existing* upstream turn. Nothing in Pi preserves that upstream turn for you. |
| **(b) Text / custom messages / UI-only updates** | Assistant text is the broadest-compatible display, but becomes assistant history and may be replayed/summarized. `sendMessage({customType,content,display:true,details})` can use `registerMessageRenderer`; `content` enters model context as a **user** message even if `display: false` (only `details` stays out). `sendMessage` has queue semantics, not a live tool-row update. **Preferred:** `ctx.ui.setWidget`/`setStatus` for transient tool/plan progress, plus `pi.appendEntry`/`registerEntryRenderer` for an optional durable, expandable TUI card with no model-context effect. |
| **(c) Built-in provider-executed tools** | No public `serverToolUse`, `providerExecuted`, `server_tool_use`, `web_search_tool_result`, or `web_search_call` block/flag in the installed pi-ai normalized types/adapters. Checked `ToolCall`, `AssistantMessage.content`, and every `AssistantMessageEvent` variant, and searched the installed pi-ai `dist`. Anthropic’s normalizer handles normal `tool_use`; OpenAI Responses normalizes `function_call` and `custom_tool_call`; these become local `ToolCall`s. Vendor wire capabilities, deferred responses, and tool namespaces are not a generic no-execute UI mechanism. |

References for (b): `CA/docs/extensions.md:1627-1649,1683-1699,3166-3207`; `CA/docs/message-types.md:227-244`; `CA/dist/core/messages.js:84-114`; `CA/docs/json.md:118-126` (`entry_appended` is observable on the wire, but client rendering is not guaranteed). For (c): `AI/dist/types.d.ts:278-291,382-413,592-646`; `AI/dist/api/anthropic-messages.js:701-750`; `AI/dist/api/openai-responses-shared.js:389-454,627-685`.

**If evaluating the proxy later:** key state by Pi session/runtime, ACP turn and call ID; let the ACP reader continue independently and buffer updates that arrive before Pi calls `execute`; never wait for a second `streamSimple` to produce the result that blocks `execute`. Handle more ACP updates/text/calls after the proxy returns, distinguish a matching tool-result continuation from new or steered user input, and never send an already-observed ACP tool result back as a fresh backend prompt. Expect real persisted synthetic tool calls/results, effects on compaction/model switches, and local validation/permissions that can block the *proxy wait* even when the backend action already ran. Use a namespaced active tool, not a built-in name; reject stale or invented IDs, and clean up buffered work on abort and branch/session replacement. Do not rely on transient `toolcall_*` events with calls removed from the final message: UI and transcript semantics would diverge. Tool-renderer examples: `CA/examples/extensions/built-in-tool-renderer.ts:92-137,140-193`; `CA/examples/extensions/question.ts:73-90,219-286` (interactive dialog plus result details); `CA/examples/extensions/permission-gate.ts:12-33` (local gate only).

**Smallest durable display path:** pass ACP updates through the parsed-event hook, handle only the selected provider and current request in the extension, update a bounded widget, and append a compact card at `turn_end` if useful. The shipped debug viewer proves the mechanism: `provider_stream_event` → collect → match assistant `message_end` → `pi.appendEntry` on `turn_end` (`CA/examples/extensions/debug-provider.ts:21-42,65-89`). Avoid copying its raw-event persistence in production. `CA/examples/extensions/entry-renderer.ts:12-40` shows TUI-only entries; `message-renderer.ts:12-32,34-57` in the same directory shows the context-bearing alternative.

## 3. Extension hooks and UI

| API / hook | Design implications |
|---|---|
| `session_start` / `session_shutdown` | Start reasons `startup`, `reload`, `new`, `resume`, `fork`; shutdown `quit`, `reload`, `new`, `resume`, `fork`. Replacement carries previous/target file where available. Use factory for registration, `session_start` for binding session state (or lazily open the ACP process at first applicable request), and async idempotent `session_shutdown` for close/kill and listener cleanup. Factories can run without a session, including discovery. `CA/docs/extensions.md:210-256,375-406,473-514,601-611`. |
| Switch, fork, and tree | `session_before_switch` (`new`/`resume`) and `session_before_fork` (`before`/`at`, fork/clone) are cancellable; successful replacement shuts down old runtime and emits `session_start` on the new one. No separate public post-`session_switch`/`session_fork` events. `/tree` stays in the same session/runtime: `session_before_tree` can cancel/override summary, `session_tree` reports the new leaf. Restore branch-relative mapping there. `CA/docs/extensions.md:496-531,575-599,1409-1512`; `CA/docs/sessions.md:35-52`; `CA/dist/core/extensions/types.d.ts:595-691`. |
| `before_agent_start` / `input` | `input` sees raw text, images, source (`interactive`, `rpc`, or `extension`) and `streamingBehavior`; can continue/transform/handle. Extension commands are checked first and bypass `input`; skill/template expansion follows it. `before_agent_start` sees expanded prompt and images, or a custom starting message, and can inject persistent context or modify the system prompt/tool selection. Neither hook identifies every provider invocation (e.g. summaries and direct SDK calls). `CA/docs/extensions.md:313-336,615-661,1112-1159`. |
| `message_start/update/end`, `agent_end`, `turn_end` | Start/end cover user, assistant, custom, and tool results; update is assistant streaming. `message_end` can replace the finalized message, keeping its role. `turn_end` runs after message/result persistence, supports validated custom drafts and guarded `continue`; avoid unconditional continuation. `agent_end` closes a low-level run, not necessarily retries, compaction recovery, or follow-ups. Use `agent_settled` to clear final run status; `agent_before_settle` is the last actionable boundary. `CA/docs/extensions.md:663-695,715-787`; `CA/docs/sdk.md:72-94`. |

## 4. Session routing, persistence, and concurrent pi-web sessions

### Request ID is available, but is not always a Pi conversation ID

Normal turns need **no event-order heuristic**. The SDK sets `Agent.sessionId` from the manager, agent core carries it in config/options, then `ModelRuntime` preserves it in `providerOptions`. The adapter receives no `ExtensionContext`; use the request ID for routing and event handlers to attach cwd, UI, branch state, and cleanup. Evidence chain:

```js
// CA/dist/core/sdk.js:268-276
return modelRuntime.streamSimple(model, context, requestOptions);
// ... Agent options:
sessionId: sessionManager.getSessionId(),
```

`AG/dist/agent.js:301-322` puts it in config, `AG/dist/agent-loop.js:265-283` spreads config into options, `CA/dist/core/model-runtime.js:471-493,523-529` forwards it. In event handlers use `ctx.sessionManager.getSessionId()` and `ctx.cwd`. The `before_provider_headers` example also adds an explicit session header for gateway tracing (`CA/docs/extensions.md:846-862`), but that is not a reliable replacement for distinguishing request purposes (even a summary may pass through the same extension runner).

**Exceptions:** direct `modelRegistry.streamSimple` calls may omit or choose the ID; default compaction and branch summaries use standalone requests with `cacheRetention: "none"` and a fresh routing ID when no ID is supplied. In the stock session compaction path the last arg is explicitly `undefined`. Cache warming can reuse a real session ID but sets `disableContinuation: true`, `maxTokens: 1`, and `maxRetries: 0`. For a side-effectful ACP backend, omit `promptCache` so models don't opt into warming; do not attach cache replays, missing IDs or unknown routing IDs to a real ACP conversation. Decide explicitly how to serve independent summary/direct requests (isolated non-mutating handling, or a clear unsupported result plus a custom summary path); don't silently feed them into the active `agy` turn. `CA/dist/core/agent-session.js:2305-2315,3440-3459`; `CA/dist/core/compaction/compaction.js:463-490`; `AI/dist/cache-warming.js:48-50`; `CA/docs/compaction.md:16-49,297-346,385-415`; `CA/docs/virtual-models.md:63-88`.

### Persisting ACP session mappings

`ctx.sessionManager` exposes **`ReadonlySessionManager`**: `getSessionId`, `getSessionFile`, `getEntries` (all entries), `getBranch` (active ancestry), `getLeafId`, `getEntry`, tree/projection/file/cwd/name accessors. **It does not expose `appendCustomEntry`.** The mutable `SessionManager` used by SDK code or `ctx.newSession({ setup(sm) { ... } })` does expose `appendCustomEntry(customType,data): string`. The supported extension path is `pi.appendEntry`, which calls that method and emits `entry_appended`. `CA/dist/core/extensions/types.d.ts:232-245,310-318,1313-1317`; `CA/dist/core/session-manager.d.ts:178,280`; `CA/dist/core/agent-session.js:2889-2895`.

```ts
// Only once an ACP session is associated with the active branch:
pi.appendEntry("agy-session", { v: 1, piId, acpId, checkpointEntryId });
// In session_start / session_tree, read the branch rather than all entries:
const mapping = ctx.sessionManager.getBranch().findLast(
  (e) => e.type === "custom" && e.customType === "agy-session",
);
```

Validate `entry.data` before use and store identifiers/checkpoints, not secrets or raw logs. `custom` entries are parent-linked JSONL entries but never projected to the LLM; they may render in TUI and appear in exports/events. In-memory sessions do not persist; in a new disk-backed session a path can already be assigned even though Pi delays writing a file until there is a user or assistant message. Forks/clone can copy an old mapping into a **new** Pi ID, and `/tree` can change history without changing the Pi ID. A branch entry alone does not rewind a mutable backend session: check ownership, workspace, branch checkpoint and model/mode, and fork/reload a verified backend checkpoint or start fresh if safe replay isn't available. A successful `session_start` with reason `resume` does not imply ACP supports loading that ID. `CA/dist/core/session-manager.js:789-815,921-933,1226-1305`; `CA/docs/session-format.md:64-76,164-186,209-248`; `CA/docs/extensions.md:2140-2178`; `CA/docs/sessions.md:54-73`.

### Concurrency and pi-web

- **SDK supports multiple sessions in the same process.** `createAgentSession()` constructs a new agent, manager and resource loader by default; `AgentSession` owns its conversation/runtime; `AgentSessionRuntime` is a separate abstraction for replacing one active session. Hosts can explicitly supply services. Keep state inside the factory for a normally isolated runtime, not in a module/global `currentSession`, and do not reuse one mutable `ResourceLoader`/provider closure across concurrent sessions unless it is deliberately session-keyed. Do not put the same JSONL session under two independent writers. `CA/docs/sdk.md:26-60,96-118`; `CA/dist/core/sdk.js:64-82,255-323`; `CA/dist/core/agent-session-services.js:65-114`; `CA/examples/sdk/06-extensions.ts:22-53`. For custom SDK hosts, ensure `bindExtensions()` fires `session_start` when needed; low-level `AgentSession.dispose()` aborts/invalidates synchronously and **does not itself emit `session_shutdown`**. `AgentSessionRuntime.dispose()` awaits shutdown first (`CA/dist/core/agent-session.js:1074-1093,2765-2820`; `CA/dist/core/agent-session-runtime.js:328-337`).
- **SDK startup caveat:** bare `createAgentSession()` looks up the initial model before constructing `AgentSession`. If the host must select an extension-provided model at startup, use `createAgentSessionServices()` → `createAgentSessionFromServices()`, as pi-web does. The services factory applies queued provider registrations and awaits a cache-only refresh before selection. The checked SDK runtime example also shows when to bind and dispose extensions. `CA/dist/core/sdk.js:64-115,300-323`; `CA/dist/core/agent-session-services.js:53-114,129-145`; `CA/examples/sdk/13-session-runtime.ts:19-60`.
- **This installed pi-web really does this in process.** `WEB/.next/server/chunks/1282.js:18` (minified, search these literal anchors) calls `createAgentSessionServices` then `createAgentSessionFromServices`, wraps the result (`new aB(ah, ...)`) and keeps live sessions in `globalThis.__piSessions = new Map` keyed by `sessionId`, with `__piStartLocks` keyed per session. It binds the inner `AgentSession` through `bindExtensions` with `mode:"rpc"` and a web UI context. That mode value does not imply a Pi subprocess per chat. This bundle implements `setStatus`/string-array `setWidget` as `extension_ui_request`s and has a host-specific custom-UI bridge. That confirms server event emission, not which frontend views render widgets or custom-entry cards. Use plain text if display is required independent of host support; test web and TUI rendering separately. Compare stock external `RpcClient`, which really spawns a child (`CA/docs/cli-integration.md:54-76`).
- **Implication:** route by `options.sessionId` inside an isolated runtime, and if sharing a transport, use an explicit runtime/session/branch key and one in-flight ACP prompt per backend conversation unless multiplexing is verified. Map per-session values from `session_start` and `session_tree`, never a process-wide "last active" ctx. Maintain one authoritative ACP/Pi cursor policy: distinguish new input from old projected history/compaction/custom messages, and invalidate/rebuild on divergence. Avoid replaying past side effects when recreating state.

## 5. Pi package layout and loading

A minimal directory can use `extensions/index.ts` by convention or an explicit manifest. No new dependency is required by Pi for loading TypeScript. Example manifest (omit unused peers):

```json
{
  "name": "pi-agy-acp",
  "version": "0.1.0",
  "keywords": ["pi-package"],
  "pi": { "extensions": ["./src/index.ts"] },
  "peerDependencies": {
    "@earendil-works/pi-coding-agent": "*",
    "@earendil-works/pi-ai": "*"
  }
}
```

`src/index.ts` exports `default function (pi: ExtensionAPI) { /* register */ }` (can be async). Additional manifest arrays: `skills`, `prompts`, `themes` with relative paths/globs/exclusions. `jiti` imports the entry without a separate build (`moduleCache: false` for the loader); Pi maps host packages and legacy aliases. Do not rely on module-global uniqueness or on vendoring a second copy of Pi. Put real runtime dependencies in `dependencies`; Pi installs them for managed npm/git packages. Host-provided Pi packages and `typebox` belong in `peerDependencies` with `"*"` per docs; use `devDependencies` only for local checking/building. A local package is not installed/copied; its own dependency tree and the `agy` executable are deployment prerequisites. `CA/docs/packages.md:33-78,100-116`; `CA/docs/extensions.md:123-170,186-213,258-303`; `CA/dist/core/extensions/loader.js:34-64,491-519`; `CA/package.json:57`.

`~/.pi/agent/settings.json`: `{"packages":["/absolute/path/to/pi-agy-acp"]}`. If the package root is the project itself, `.pi/settings.json` can use `{"packages":[".."]}`; resolution is relative to the containing settings file, not the process cwd. A single file can instead be listed in `extensions`, or tried via `pi -e ./src/index.ts`. Project settings/packages need project trust; `/reload` is for discovered resources. `CA/docs/packages.md:7-44,118-153`; `CA/docs/settings.md:149-165`; `CA/docs/security.md:24-58`; `CA/docs/slash-commands.md:43-61`.

## 6. Images

```ts
const image: ImageContent = { type: "image", data: base64Bytes, mimeType: "image/png" };
const message: UserMessage = {
  role: "user", content: [{ type: "text", text: "Describe this" }, image], timestamp: Date.now(),
};
```

`data` is base64 bytes, not a file path or a full data URL. `pi.sendUserMessage` accepts the array directly; RPC `prompt` has `message` and separate `images`. Advertise `input: ["text", "image"]` only if the ACP session and selected backend model accept images. Built-in adapters downgrade unsupported images but `ModelRuntime` only normalizes the transcript before custom dispatch; your adapter must handle `model.input`, report unsupported images or represent omission explicitly, and map supported images to ACP only after checking capability. `images.blockImages` replaces user/tool-result images upstream of dispatch. `inputLimits.images.resize` affects new images before storage, not history already written; max-count/bytes metadata does not in general rewrite or reject old history. Chat `AssistantMessage.content` has **no** image block; images are valid in tool results or user/custom messages, not arbitrary assistant blocks. `AI/dist/types.d.ts:273-277,377-388,434-450,647-659`; `AI/dist/api/transform-messages.js:1-70`; `CA/dist/core/model-runtime.js:504-529`; `CA/dist/core/sdk.js:161-189`; `CA/docs/models.md:81-112`; `CA/docs/settings.md:105-114`; `CA/docs/rpc-commands.md:7-19`.

## 7. Integration pitfalls and first checks

1. **Permissions are upstream of display.** Pi tool gates, allowlists, project trust and `toolChoice` do not authorize/control tools already being executed by ACP. Use the backend's actual permission-request path, if present, with an abortable `ctx.ui` dialog and explicit denial when there is no usable UI. Trust is a load decision, not isolation. Never auto-approve or start a subprocess from mere model discovery. Keep raw output redacted and bounded; do not log prompts, tokens, provider-scoped env, file contents or full ACP events by default. `CA/docs/security.md:1-30`; `CA/docs/custom-provider.md:3-5,126-143`; `CA/docs/extensions.md:2451-2500`.
2. **The Pi transcript and ACP session can drift.** Pi compaction, `/tree`, fork/clone, model switches, context edits, retries and steering change what Pi sends. Do not silently ignore that in a stateful bridge. Prefer one owner of the live backend turn; no implicit replay after disconnect or retry once side effects may have run. Report cancellation as `aborted`; normalize only confirmed overflow to `context_length_exceeded`, never auth/quota/network errors. Stock retry can re-enter the provider. A virtual model is optional routing, not an ACP transport: it routes to a physical model with `user/continuation/retry/direct` reasons and optional branch-relative state; `streamSimple` still receives the physical model and normal options. `CA/docs/custom-provider.md:202-225`; `CA/docs/virtual-models.md:13-36,63-109`; `CA/docs/session-format.md:139-147,224-248`; `CA/docs/settings.md:116-135`.
3. **Minimum acceptance cases (not run):** exercise a fake ACP stream with interleaved text/thought/tool/plan updates; assert balanced indexes and exactly one terminal event, including empty output, malformed stream, early setup failure, and abort. Assert no Pi tool execution and no tool/plan cards in the projected model history on the recommended path. Verify a parallel pair of sessions (including cancellation of only one), reload/resume and `/tree`/fork mapping, non-turn summary/cache calls, retries after partial output, permission cancel/no-UI, and vision plus text-only behavior. On the real CLI verify discovery/model/effort controls, session load/resume, permission behavior, image handling, stop/usage semantics and whether cancellation really stops backend work. Check actual pi-web UI display, not just server event emission. `CA/docs/custom-provider.md:210-227`; `CA/docs/json.md:61-126`.
