## 1. 进程：何时启动，如何退出

- **实际命令：** 可执行文件解析顺序为显式 `binaryPath` → managed active release → 兼容的 `PATH` CLI；显式路径不因 managed 更新被换掉。传给 ACP launch 的参数是下例；聊天的 `cwd` 是 `runtimePolicy.cwd ?? process.cwd()`（通常项目或 worktree），probe/login 使用独立临时 cwd；安装验证用临时 profile 目录。参数是 argv，不拼接用户 shell 命令；平台启动器可包一层（例如 Linux `exec`/systemd，Windows shim）。managed 包有 scope lease，不原地替换活跃 binary。依据：`P/AntigravityInstallation.ts:615-730,744-787`、`P/antigravityAuthSupport.ts:546-572`、`P/Drivers/AntigravityDriver.ts:227-336,378-408,424-453`、`R/adapter.ts:2831-2851`、`R/AcpSessionRuntime.ts:1433-1522`、`docs/user/providers-antigravity.md:51-70`。

  ```ts
  // T3 的聊天启动参数（不是登录命令）
  command = executablePath
  args = ["acp", "--gemini-dir", absoluteProfile, "--app-data-dir", "antigravity-acp"]
  // --app-data-dir 是 gemini-dir 下的名字，不是另一个绝对路径。
  ```

- **精确 env 规则：** 基础是 provider process env + thread env（MCP 可注入 `T3CODE_THREAD_ID`、`T3_ACP_MCP_ENDPOINT/AUTHORIZATION/NODE`，可选 `ENTRYPOINT/CALL`），然后 case-insensitive 删除 `GEMINI_API_KEY`, `GOOGLE_API_KEY`, `GOOGLE_APPLICATION_CREDENTIALS`, `GOOGLE_CLOUD_PROJECT`, `GOOGLE_CLOUD_LOCATION`, `GOOGLE_CLOUD_QUOTA_PROJECT`, `GOOGLE_GENAI_USE_VERTEXAI`, `GCLOUD_PROJECT`, `CLOUDSDK_CORE_PROJECT`, `AGY_ACP_CCPA_PROJECT`, `AGY_ACP_ENABLE_OAUTH`, `GEMINI_HOME`, `AGY_ACP_FORCE_FILE_STORAGE`, `AGY_CLI_DISABLE_AUTO_UPDATE`, `BROWSER`, `PYTHONUNBUFFERED`, `ELECTRON_RUN_AS_NODE`, `CHROME_CRASHPAD_PIPE_NAME`。再设 `GEMINI_HOME=<profile>`, `AGY_ACP_FORCE_FILE_STORAGE=1`, `AGY_CLI_DISABLE_AUTO_UPDATE=1`, `BROWSER=<受控 Node helper>`, `PYTHONUNBUFFERED=1`, `ELECTRON_RUN_AS_NODE=1`；仅 personal OAuth 补 `SSH_CONNECTION`（优先已有，否则 `127.0.0.1 0 127.0.0.1 0`）；Windows `TEMP`/`TMP`，其他平台 `TMPDIR`，指向每个进程的 `run-*` 临时目录。必要时设置 Linux `SSL_CERT_FILE`，不覆盖已有 `SSL_CERT_FILE`/`SSL_CERT_DIR`。只按所选方式注入 `GEMINI_API_KEY` 或 `GOOGLE_API_KEY`；GCP project/location 与 `auth.type` 写 profile `settings.json`，不把 key 写进去。`extendEnv:false` 防止 spawner 把删过的环境补回来；不是清空所有环境（例如不主动删除通用代理变量）。依据：`P/antigravityAuthSupport.ts:62-82,125-155,185-244,425-469,546-572`、`P/Drivers/AntigravityDriver.ts:277-336`、`R/adapter.ts:1083-1096`、`P/acp/AcpJsonRpcConnection.test.ts:566-586`。

- **Lazy，但不是每次 prompt spawn。** 健康轮询只 resolve 安装并返回合成的 metadata，不启动 `agy`（其中的 `protocolVersion:1` **不是**线上握手）；聊天在需要打开 provider session 时启动，连接复用于该线程多个 turn。通用 adapter 声明 `supportsMultipleProviderThreadsPerSession:false`；manager 不把同一个非共享 runtime 附给另一线程。安装验证、登录、手动模型刷新和文本生成有独立的短命 runtime；相同 provider instance 的并行聊天进程共享 profile 而不是共享 stdio/ACP 连接。依据：`P/Drivers/AntigravityDriver.ts:378-420,540-577,622-677`、`R/adapter.ts:813-824,7753-7796,8007-8036`、`O/ProviderSessionManager.ts:3170-3184,3226-3240,3286-3293`。

- **崩溃与重启。** `effect-acp` reader EOF 后给退出状态 250 ms，带 PID/exit code 或 signal；reader 异常也终止连接，让 pending RPC 失败，不一直等。Runtime 收集有界、经清理的 stderr 尾部，只记录一次 termination 并关闭 scope；adapter 给当前 generation 标记 `runtimeRestartRequired`，失去 transport 的 prompt 或只剩后台工作的 turn 会失败。下一次需要连接时再起，不后台无限重启，也不盲重放失败 prompt；旧 generation 的回调不能混进新 run。依据：`E/protocol.ts:545-568,864-888`、`E/_internal/stdio.ts:52-75`、`R/AcpSessionRuntime.ts:1332-1387,1698-1738`、`R/adapter.ts:2769-2830,9077-9095,9290-9328,10042-10066`；idle exit 回归 `P/acp/AcpJsonRpcConnection.test.ts:342-398`。

- **进程树要分三层看。** 正常 close 可尝试已协商的 `session/close`（最多 10 s），再关 runtime scope。Antigravity **没有设置** shared runtime 的 `ownDetachedProcessGroup` 或 `ownDescendantProcessGroups`；不应由此推断 OS child 不 detached：T3 server 的实际 Node spawner 默认 **POSIX `detached:true`，Windows `false`**。其 scope release 在 POSIX 给 `-child.pid` 发 TERM（失败可落回 child，设了 `forceKillAfter` 才升级 KILL）；Windows 对还在的 leader 用 `taskkill /pid <pid> /T /F`，leader 已退出时跳过。ACP 超时 retire 显式传 `forceKillAfter:"1 second"`。依据：`R/adapter.ts:9868-9893`、`P/acp/AntigravityAcpSupport.ts:114-154`、`R/AcpSessionRuntime.ts:1509-1524,2569-2574`、`apps/server/src/server.ts:369,1410,1420`、`apps/server/src/process/SpawnWorker.ts:551-568`、`patches/@effect__platform-node-shared@4.1.5.patch:42-70,75-90`；外部锁定依赖 [platform-node-shared 4.1.5 tarball](https://registry.npmjs.org/@effect/platform-node-shared/-/platform-node-shared-4.1.5.tgz) 内 `package/dist/internal/nodeChildProcessSpawner.js:1-8` 和 `package/dist/NodeChildProcessSpawner.js:359-435,488-526`（`pnpm-lock.yaml:327,368`）。

- **脱离原进程组的孙进程。** Linux 有可用的 user systemd 时，T3 再把无 shell 的 launcher 放进每次启动独有的 `t3code-acp-*.scope`；root exit 或 finalizer 时尝试 `systemctl --user stop --no-block <unit>`，可回收离开原 PGID 但仍在该 scope 的后代。无 systemd 的 fallback 不能保证回收另建 session 的进程。shared runtime 另有显式 opt-in 的更强路径（Linux cgroup v2 lease / `cgroup.kill`；不可用时 `/proc` ownership ledger，按 PID 身份及父子关系回收；基础组 TERM→KILL，Windows tree kill），HEAD 是 **Grok** 调用，不是 agy。测试覆盖 TERM 时再 fork、未知 group 成员落回精确 PID、PID 重用不碰 T3 session、zombie、leader 先退出和重试。没有查到按 `language_server` 或 hub 进程名扫描/关闭的 Antigravity 逻辑；隔离 profile + 只管自己的 child/group/unit，不等于证明所有 agy 版本绝不共享/接触已有 daemon。不要加 `pkill agy` 或 kill 全局 hub。依据：`R/AcpSessionRuntime.ts:1440-1507,1534-1540,1542-1696`、`apps/server/src/process/agentScope.ts:160-182,359-382,426-462`、`packages/shared/src/AgentScope.ts:92-120`、`packages/provider-grok/src/server/acpSupport.ts:84-94,131-147`、`P/acp/AcpSessionRuntime.processTree.test.ts:85,137,347,513-611,612,691,755,844`。

## 2. 会话握手、历史和持久化

- **`initialize`，实际 wire：** 请求发 `protocolVersion:2`，同时发精简 v2 的 `info/capabilities` 和 v1 的 `clientInfo/clientCapabilities`。返回是否有 `info` 才决定 v2 方法/字段；Antigravity 有返回数字 `2` 但实际是 v1 `agentInfo/agentCapabilities` 的 fixture，不能只看数字。聊天的 v1 `fs` 是 `{readTextFile:true,writeTextFile:false}`，`terminal:false`，另有 `session:{notices:{},compaction:{}}`、`elicitation:{form:{}}`；helper/probe 默认 `readTextFile:false`，并非全都提供 fs。已知安装版本 ≥1.5.1 用 `t3-code` / `T3 Code` / package version；更旧或版本未知（例如初次 PATH/custom 启动）用 `zed/0.0.0`，是历史 allowlist shim，不是协议要求。HEAD 只服务 `fs/read_text_file`：绝对路径、realpath 检查，根目录为当前 turn workspace/attachments，支持 1-based `line` 与 `limit`；不开 write，避免 agy 选整文件 `client_edit_file` 而非原生 diff 编辑。依据：`R/AcpSessionRuntime.ts:1852-1867,2289-2304`、`R/adapter.ts:2853-2862`、`E/client.ts:693-723,1100-1129`、`packages/effect-acp/test/fixtures/antigravity-initialize.json:1-21,44-48`、`P/acp/AntigravityAcpSupport.ts:74-149`、`O/Adapters/AntigravityAdapterV2.ts:145-165,272-282`、`P/acp/AntigravityClientFiles.ts:24-110`、`O/Adapters/AntigravityAdapterV2.test.ts:369-524`。

- **`session/new`：** `{cwd, mcpServers, ...optionalSetupFields}`；`session/resume` / `session/load` 再带 `sessionId`。无 MCP context（setup/refresh/text generation）发 `[]`；有 context 时优先协商 `{type:"acp",name:"t3-code",serverId:"t3-code"}`，其次 agent 明示 `mcpCapabilities.http` 时给 HTTP endpoint + `Authorization` header，最后 `t3-code` stdio bridge。只在能力 `_meta.antigravity.systemPrompt.append === true` 时注入 `_meta:{antigravity:{systemPrompt:{append:...}}}`（聊天中为 PR linking instructions）。Runtime 支持显式 `additionalDirectories` 和有 `sessionCapabilities.additionalDirectories` 才附加的 workspace `extraRoots`；**HEAD 的 Antigravity 聊天路径没有硬塞 attachments dir 到该字段**，PR #9348 当时这么做不等于现在；当前 attachments 通过路径提示和受限 client read 到达。依据：`R/AcpSessionRuntime.ts:2339-2367,2418-2468`、`R/adapter.ts:1042-1082,2839-2851`、`O/Adapters/AntigravityAdapterV2.ts:151-164,224-229`、`P/acp/AntigravityAcpSupport.ts:86-104`、`P/Drivers/AntigravityDriver.ts:404-408,652-660`。

- **不是所有恢复都同一个 RPC。** Antigravity在冷启动拿到已保存 ID 时，设 `resumeMethod:"resume"`，要求 capability `sessionCapabilities.resume`，走 no-history `session/resume`，即使 `loadSession:true`；无 resume 能力则报 -32601，不自动在这一分支改走 load。Generic 冷启动默认优先 `session/load`；已打开 runtime 后调用 `activateSession`（例如 crash 后重新激活或切换 native ID）也还是优先 load、其次 resume。已经是 active ID 则 `resumeThread` 不重复激活。依据：`P/acp/AntigravityAcpSupport.ts:121-135`、`R/AcpSessionRuntime.ts:2425-2469,2676-2707`、`R/adapter.ts:8007-8079,10029-10075`。

- **实时输出 vs replay。** runtime 在 Starting 状态丢弃聊天和工具输出，只按 `(sessionId, update kind)` 保留最新的 `current_mode_update`、`config_option_update`、`available_commands_update`，成功后只应用目标 session 的 metadata。`session/load` 时 gate 只隔离正在加载的 session，避免冲掉别的 session 活跃 prompt；普通 replay 不进直播，候选 config 不提前覆盖 live；显式 `params._meta.isReplay === true` 的帧也不是实时输出。adapter 侧可将 replay 投到 `recordLoadedHistory`/snapshot，而非 turn/wake。默认等 load RPC response；只有显式 opt-in 才允许 replay idle 先就绪（默认 gap 2 s），迟来的 response 不能覆盖已发生的 mode/config 写或更新。这不是文本比较去重。依据：`R/AcpSessionRuntime.ts:87-91,1773-1845,1961-2010,2026-2078,2117-2189,2517-2542,3021-3028`、`R/runtimeModel.ts:1319-1357`、`R/adapter.ts:7047-7058`、`P/acp/AcpJsonRpcConnection.test.ts:1199-1226,1227-1411,1412-1514`。

- **映射和导入。** 不是从 cwd 或进程 PID 重推 ID：provider thread 行有 `appThreadId`、`providerInstanceId` 和 strong `nativeThreadRef:{driver,nativeId:sessionId,strength:"strong"}`；SQLite `orchestration_v2_projection_provider_threads.payload_json` 持久化，后续开 runtime 把 `nativeId` 作为 `initialNativeThreadId`。Registry import 另做 deterministic app thread ID = `(driver,instanceId,sessionId)`，SQL 查 owner、忽略 deleted，按 mutation gate 串行绑定，另由 `AgentSessionImporter` 复制历史（失败可修复）。HEAD 的 built-in Antigravity driver 没有返回 `acpSessionManagement`，不要把 Registry UI 的 list/import 直接算作内置 agy 功能。依据：`R/adapter.ts:1124-1165,9988-10013`、`O/ProjectionStore.ts:2894-2938`、`O/ProviderTurnStartService.ts:961-985`、`P/AcpRegistrySessions.ts:30-39,79-104,128-198,209-266`、`P/Drivers/AntigravityDriver.ts:714-743`、`docs/user/providers-acp.md:93-106`。

- **失败和 fork。** 原始 load 失败是错误，不是假成功；冷开 adapter 对 `session/load` / `session/resume` 方法失败保存原 error、起一个干净候选，之后目标 ID 的激活会看到该 error。上层只有可安全替代时才新开/采用 fresh native thread，把保留上下文作为 handoff；若 thread 正被使用，或结果未知（可能已经 resume 但没回），不擅自分裂成新的对话。live 换 session 时先等候选成功再替换，失败保留旧配置/连接。`session/fork` 仅在 `sessionCapabilities.fork` 非空时可用，送源 `sessionId/cwd/mcpServers`，采纳返回的新 ID 并存 `forkedFrom`；一般只 fork head，历史 turn 需要 flavor 的 native turn 选择支持，Antigravity 无该 hook，已读 fixture 也没广告 fork。无 native rewind 不代表 UI 无法编辑早期消息：回退保留的历史在新的 ACP 会话 handoff。依据：`R/adapter.ts:922-948,959-996,7798-7967,8009-8031,8054-8079,10705-10775`、`R/AcpSessionRuntime.ts:2708-2726`、`O/ProviderTurnStartService.ts:1685-1797`、`packages/effect-acp/test/fixtures/antigravity-initialize.json:14-17`、`docs/user/providers-antigravity.md:88-91`。

## 3. 模型、thinking 和 mode

- **发现和 cache：** 登录验证/聊天 `session/new` 或 `resume` 的 setup response 装入 provider snapshot；`config_option_update` 与 set RPC response 动态更新，成功握手后的命令 metadata 也更新。Runtime 避免重发已生效的值，in-flight 收到 config notification 时不拿旧 RPC response 覆盖。`thinkingLevels` 是每个 instance 内存的 model→descriptor（`null` 表示实测无选项），没观察到的 model 暂借当前 options 但不借 `currentValue`；显式刷新/登录在临时 session 中（若起始模型报告 thinking）依次切到各模型并切回原模型，监听事件后 drain。Registry 按 instance 将完整 snapshot 写 status cache，重启可保留已见 catalog 与 saved auth，普通 health check 不等于真实重新验权；明确 auth required/sign-out 清空账户 metadata，非 auth 的 refresh 错误不把 catalog 擦掉。依据：`R/AcpSessionRuntime.ts:2227-2287,2494-2502`、`P/Drivers/AntigravityDriver.ts:496-525,540-577,634-642,663-710`、`P/AntigravityProvider.ts:63-121,239-262,405-470,508-538`、`P/ProviderRegistry.ts:239-255,303-351,482-512,560-574`。

## 4. 权限与提问

- **Wire 以 optionId 为准。** Agent 发 `session/request_permission {sessionId,toolCall,options:[{optionId,name,kind,...}]}`，可用已见的同 ID tool state 补齐稀疏请求；返回 `{outcome:{outcome:"selected",optionId}}` 或 `{outcome:{outcome:"cancelled"}}`。`allow_once` → Allow once，`allow_always` → Allow for this thread（由 agent 解释，可能实际持久化），`reject_once` → Deny；协议也有 `reject_always`，T3 agy 卡不单独提供它。自动允许优先 `allow_once`，没有才用 `allow_always`；拒绝无 `reject_once` 时 cancelled。`_meta["agy.security.warning"]` 的 message/title 有界化，web tooltip / mobile inline。审批节点以 command / file-read / file-change 区分，带对应 command/diff 项；等待 UI decision 并关联原 transport response，Stop/teardown 清理。依据：`E/_generated/schema-v1.gen.ts:859-872,3150-3174`、`P/acp/AntigravityProtocol.ts:69-115`、`R/adapter.ts:1542-1557,1604-1625,6332-6450,7325-7498,10432-10467`、`apps/web/src/components/chat/ComposerPendingApprovalActions.tsx:68-105`、`apps/mobile/src/features/threads/PendingApprovalCard.tsx:39-60`。

- **策略而非盲映射。** 逻辑映射 `approval-required → default`, `auto-accept-edits → auto_edit`, `auto → auto`, `full-access → yolo`。但 agy CLI 拒绝 `yolo`/`auto_edit`；实际在 `default` 下由 client 按 live policy 答，只有 agent 报 `auto` 才切 native Auto。通常 Supervised 问除 read/search/think 之外的操作；Auto-accept edits 可放行 edit/delete/move；Full access 通常自动答允许；**agy 的 Auto 已经过 agent 自己的审核，仍发来的请求 T3 默认问人**。沿用 sandbox deny/显式审批约束，workspaceWrite 自动允许的 edit 要证明路径在可写根下，不能把它当 OS sandbox；对 T3 自己授权的 MCP，Auto/Auto-accept edits 在条件满足时可直接通过，但只认明确 `ServerName:"t3-code"` + known `ToolName` 或准确的 `Run mcp_t3-code_<tool>?`，不拿 `Running <tool>` 或 shell command 标题作信任凭证。mode 选择不能超过 thread 的权限上限。依据：`P/acp/AntigravityAcpSupport.ts:156-235`、`P/Drivers/AntigravityDriver.ts:358-365`、`R/clientPolicy.ts:77-201`、`R/adapter.ts:8186-8219,8290-8295`、`O/Adapters/AntigravityAdapterV2.test.ts:2282-2301`。

## 5. 工具、命令、diff 和 agy 的异形事件

- **以 ID 合并，不每帧建卡。** `tool_call` / `tool_call_update`（更新可只有 ID+status）按 active turn 的 `toolCallId` 合并；native UI ID 加 session scope。记录 `title/kind/status/rawInput/rawOutput/content/locations/_meta`；空 title/缺字段不覆盖旧 title，明确 null 在兼容层要能清除对应字段。ACP v1 kinds 是 `read/edit/delete/move/search/execute/think/fetch/switch_mode/other`；`pending/in_progress/completed/failed` → pending/running/completed/failed；generic 将适配到的 `cancelled`/Stop late 状态转成失败/中断语义。`locations` 保留 path/line，缺失时会从 diff 或输入提取 path；UI 语义是 command_execution、file_change、read/search/web_search、MCP 或普通 dynamic tool。重复/增量进度合并并 coalesce，状态变化要出；同一 ID 的重复完成不是又执行一次。没有找到 agy 普遍为**不同调用**分配同一 ID 的代码证据；有重复完成、迟到更新、replay 的证据。依据：`E/_generated/schema-v1.gen.ts:576-601,625-661,6524-6545`、`R/runtimeModel.ts:512-529,585-647,801-975,979-1082`、`R/adapter.ts:4417-4430,4599-4629,4753-4769,4790-4905,5359-5384`、`P/acp/AcpJsonRpcConnection.test.ts:1022-1067`。

## 7. 图片与附件

会话 `session/prompt` 的 `prompt` 是 ACP `ContentBlock[]`，`data` 是**原始 bytes 的 base64**，不是 `data:` URI。以下结构源于 `R/AcpSessionRuntime.ts:2838-2855`、`P/acp/AntigravityAcpSupport.ts:406-527`：

```ts
{sessionId, prompt: [
  {type: "text", text: "Describe this image"},
  {type: "image", mimeType: "image/png", data: bytes.toString("base64")},
]}
```

- 整体 composer 可展示 image 支持（agy flavor 声明 true），但**真正 native embed** 必须 `initialize.agentCapabilities.promptCapabilities.image === true` 且 MIME 是 BMP/JPEG/PNG/WebP。否则留文本里的已存路径，不硬塞 image block。检查实际文件/大小：单图 10 MiB，native attachments 总计 50 MiB，读取上限含多一字节并复核，防止大小变化；不支持或过大的普通文件走路径。音频有 audio capability/20 MiB 限制，PDF：`resource_link`，文本：`resource`（embeddedContext capability，1 MiB，有界并严格解码 UTF-8/UTF-16）；其他文件或折叠粘贴走路径。注意：base64 增长后仍需 transport 单行预算，不能直接拿界面 byte limit 当 wire size。依据：`O/Adapters/AntigravityAdapterV2.ts:229-236,290-296`、`R/adapter.ts:720-725,8970-8996,9738-9746`、`P/acp/AntigravityAcpSupport.ts:324-342,403-545`、`P/antigravityAuthSupport.ts:33-39,680-696`、`P/acp/AntigravityAcpSupport.test.ts:345-367,464-559,560-705`。

## 8. Stop、等待和 steering

- **Stop：** 发送 JSON-RPC notification `{"jsonrpc":"2.0","method":"session/cancel","params":{"sessionId":"s"}}`，没有 cancel RPC response。agy 用 `wait-for-prompt`：最多等待默认 15 s 让目标 prompt 入发送队列（否则 agent 会丢早到的 cancel），dispatch permit 防止下一条 prompt 越过 cancel。然后等待原 prompt RPC 结束、bookkeeping 和已读事件的 drain barrier；常见响应是原 prompt 的 `{stopReason:"cancelled"}`，投影为用户 Stop 的 `interrupted`，但实现**没有把必须等到字面 `cancelled` 作为谓词**，自然结束先到也能完成等待。超时 retire 进程，绝不让下一条 prompt 不知情地复用。Stop 可以在 prompt 已 settled 时取消 session 后台工作，soft follow-up 不这么做。依据：`P/acp/AntigravityAcpSupport.ts:121-135`、`R/AcpSessionRuntime.ts:87-91,2552-2640,2920-2925`、`R/adapter.ts:9223-9233,10267-10289,10432-10485`、`P/acp/AcpJsonRpcConnection.test.ts:257-341,1602-1695`、`O/Adapters/AntigravityAdapterV2.test.ts:1985-2015`。

- **Steer 与 Queue 是两件事。** `agentInfo.version >= 1.5.0` 则 `steersWithPrompt`：同一 session、同一应用 turn 上再发一次 `session/prompt`（含正常附件），释放前一个 prompt 的 serialization permit，但不取消其 RPC/杀其子代理；跟随最新 prompt 结算，旧结果用 generation/superseded guard 隔开。通用 helper 对明确 `Agent is already processing…` 每 1 s 试，Stop/settled/superseded 就停；不要把错误当作一律可重试。普通 Queue 等当前 turn 完再发，正在跑 native `/goal` 时普通 follow-up 也等；1.4 harness 据代码只会排队，不能启用这条 native steer。依据：`P/acp/AntigravityAcpSupport.ts:74-84`、`O/Adapters/AntigravityAdapterV2.ts:247-254`、`R/adapter.ts:152-184,9097-9132,9169-9177,9735-9828,10105-10119`、`R/AcpSessionRuntime.ts:2871-2918`、`O/Adapters/AntigravityAdapterV2.test.ts:1677-1757,1759-1893`、`docs/user/composer.md:64-83`、`docs/user/providers-antigravity.md:146-153`。

## 9. 错误、认证和 quota

- **Auth 方法与起手。** 已知 ID：`oauth-personal`、`oauth-business`、`gemini-api-key`、`agent-platform`；旧 fixture 四个都列出，线上不保证全广告。agy eager-auth 在 `initialize` 之后、new/resume 之前直接送配置的 `authenticate {methodId}`（v1；真正 v2 用 `auth/login`）；agent 可能接受未列出的 API key/Vertex 方法，不由 T3 擅自换账号方式。shared fallback 在 session setup 的 `-32000` 后才挑明确/agent-managed auth method、拒绝不匹配的 configured method 或依赖 terminal 的 headless 方法，最多 auth 后重试一次 setup。Happy path 不应把 auth-required 当成普通 transport retry。依据：`packages/effect-acp/test/fixtures/antigravity-initialize.json:22-43`、`P/antigravityAuthSupport.ts:101-155`、`E/client.ts:1123-1133`、`R/AcpSessionRuntime.ts:1077-1090,2372-2414,2474-2492`、`docs/user/providers-antigravity.md:29-43`。

## 11. 测试怎么造假 agent

1. **可编排真实子进程** `apps/server/scripts/acp-mock-agent.ts:19-119,509-651,2192-2233`：`EffectAcpAgent.layerStdio` 注册 bidirectional handlers，`NodeRuntime.runMain` 跑 CLI；`T3_ACP_ANTIGRAVITY=1`、`T3_ACP_AGENT_VERSION`、`T3_ACP_REQUEST_LOG_PATH` 等 env 开关决定脚本行为；request log 只录收到的 raw NDJSON 到测试文件，stdout 保持协议专用（故障注入除外），信号有确定退出。`mock-session-1`、`gemini-test-low/high` 和模拟 modes 是 fixture，不当成真实 agy IDs。默认 mock initialize 用真 v2 `info` shape，另可用 Antigravity v1 fixture 测协商。依据：该脚本 `114-159,369-408,543-584`、`E/agent.ts:214-271`、`E/client.test.ts:34`。
2. **有状态 handlers，时序可控。** `authenticate` 改 auth 状态，没登录返 `authRequired()`；new 提前发 commands，resume 发 startup marker，load 可先 replay/延迟回包/失败/一直挂；set-config 改模型/模式，prompt 脚本发 chunks、tool updates、反向 permission 或 fs，cancel 用 Deferred 可等到外部触发才回、保证 late updates 发生；还可 flood stderr、发其他 session 的帧、触发 `_test/exit`。验证实际出入帧与投影，不用 sleep 当同步。依据：`apps/server/scripts/acp-mock-agent.ts:584-792,871-939,1849-1884,2092-2199`、`P/acp/AcpJsonRpcConnection.test.ts:72-179,257-341,342-398,510-535,1412-1514`、`O/Adapters/AntigravityAdapterV2.test.ts:1009-1119,1677-1757`。
3. **实录 replay 单独一层。** `apps/server/scripts/acp-replay-agent.ts:6-94,110-196,204-323` 不需要 Effect：`readline` + NDJSON；transcript 为 `expect_outbound` / `emit_inbound` / `runtime_exit`，logical frame 以 kind/method 比较，不锁死 JSON-RPC ID；agent requests 给 fresh ID，responses 回接实际 ID；`<workspace>` 做跨机器替换，`<any>` 作匹配，object keys 必须一致。进度/差异写原子 status 文件，前一批记录出现 `runtime_exit` 后下一个进程可从 cursor 续；先写 status 再发送 frames，避免最后一次 RPC 回来即被杀而漏计。当前 client request ID map **按 method**，不能无脑用来还原两个并发的同方法 prompt；steer 测试用可编排 mock 或改用按实例/请求序号的 transcript。Testkit 用 transcript 文件避免 env 大小限制，可插 gate 暂扣某条 stdout。依据：`O/Adapters/AcpAdapterV2.testkit.ts:197-252`。
4. **进程与真实线的两种测试，不混用。** `P/acp/AcpSessionRuntime.processTree.test.ts:31-84,513-611,755-816` 用可注入的 process ownership controller 模型验证身份/组/race；`P/acp/AcpJsonRpcConnection.test.ts:777-833,871-1067` 通过 scoped child 走真正 stdio，验证 `initialize → new → prompt → events`、坏时序与 status-only 更新。图片、读根、权限、edit patch、429 专测分别在 `P/acp/AntigravityAcpSupport.test.ts:345-705`、`O/Adapters/AntigravityAdapterV2.test.ts:121-168,369-688`、`P/acp/AntigravityEditLocation.test.ts`、`P/acp/AntigravityTurnOutcome.test.ts:94-158`。

## 对 pi 扩展的启示

1. **先支持用户安装的原生 `agy`（以 1.5.12+ 为目标）**：按独立 argv 启动，不捆 `.par`、做自动安装器或模仿 `zed` 名字；记录握手实测的兼容范围。见 §1/§10。
2. **一个会话一个 lazy child，定义可证明的清理边界**：只处理自己创建的 PID/PGID 或 OS scope，不扫 `language_server`/hub；Windows 与脱离 process group 的后代要单独验证。见 §1。
3. **协议以 shape/capability 为准**：一个小的双向 NDJSON transport，拆帧、关联 ID、并行 drain stderr、有界内容、退出立即拒绝 pending；只过滤已知 auth 旁路，不吞任意坏 stdout。见 §2/§10。
4. **持久化 native session ID、实例/profile、workspace 和已选模型**：冷恢复优先 `session/resume`，历史与 live 分渠道；失败要能清楚说明是否开了新会话，不自动重发可能已执行的 prompt。暂缓 native fork/import。见 §2。
5. **让模型自描述**：用 `model` 和 `category:"thought_level"` 控件的实际 ID/value，切 model 后再应用 effort，未知选项别造值；按 profile cache，不把 demo 值写死。见 §3。
6. **先把权限/question 做对**：默认只授权所需 client capabilities；用 optionId 和 least-privilege；`interaction_*` 要人回答，不把 title 当授权证明，不把 ACP approval 当沙箱。见 §4。
7. **正确投影比丰富 UI 优先**：分正文/理由/工具/mode/usage，工具按 session + ID 更新；保留状态/command/exit/diff，有 snippet 就诚实显示，别假造行号、执行状态或子代理结果。见 §5/§6。
8. **图片按协商、限量嵌入**：首版只做实际支持的 image ContentBlocks，校验 base64 后的帧预算；不为附件或 terminal 方便直接扩大访问范围。见 §7。
9. **Queue、Stop、Steer 分开**：优先实现 Queue + wait-for-prompt Stop；有版本和并发测试才加同 session prompt-steer。把 auth-required、exit、quota 分开呈现；先依赖 CLI 登录，别复制 T3 的 OAuth UI、keyring hack 或 SQLite 私有格式当首版依赖。见 §8/§9。
10. **先做小型脚本 mock + 一份脱敏实录**：用 Deferred/栅栏测试启动 metadata、取消乱序、失败恢复、双向权限与进程退出，另做最小真实 CLI smoke。这里未操作真实 CLI；实际 1.5.x model/effort 矩阵、daemon 副作用及多平台树回收仍需验证。见 §10/§11。
